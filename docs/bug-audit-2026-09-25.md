# 2026-09-25 定向 Bug 检查报告

## 范围与结论

检查当前源码中的下载画质选择/确认、同任务重新下载、字幕设置到渲染的传递，以及新增本地翻译模型的切换和取消。

本轮是诊断，不是修复：未修改业务代码、安装程序、用户任务数据库或已有视频；只新增本报告与 `.debug-out/quality_audit_20260925.py` 离线复现脚本。没有访问 YouTube、调用付费 API、加载本地模型或重新跑全套测试。不能据此声称没有其他 Bug，也不能仅凭本轮推断用户截图对应原片的真实分辨率。

已找到 8 项具体问题。P1 表示优先修复的数据损失、核心结果错误或功能阻断；P2 表示操作/状态不一致。

## 1. [P1] 重新下载中断会覆盖旧原片

- 触发：同一任务、相同视频 ID 重新执行获取素材，写入期间取消或失败；单文件下载及同名输出会受影响。
- 原因：`download.py:475` 的模板始终写到同一目录/ID；`download.py:504` 同时启用 `overwrites=True`、`continuedl=False`、`nopart=True`，没有候选文件验证后替换。
- 证据：使用真正的 yt-dlp HTTP 下载器、内存模拟网络响应，在临时目录写入一个 23,000 字节旧文件。取消后只剩 3,072 字节，`previous_file_preserved=false`。这不是用户的视频文件。
- 后果：旧素材指针仍在，但文件已经损坏；以前的成片不一定丢失，却可能无法再提取字幕或重新渲染。
- 建议：每次获取写入独立候选路径，验证成功后才切换活动素材；取消只清理本次候选文件。

## 2. [P1] 低清流仍可绕过确认并被报告为画质通过

- 触发：选择 1080p，但本次可选流只有 360p；没有先读取元数据就创建草稿，或从历史任务继续获取。
- 原因：`App.tsx:1588` 的确认只在创建草稿时、且存在 `metadata` 才运行；`App.tsx:1750` 的单阶段执行及一键运行/恢复不执行同样确认。服务端 `workbench_api.py:1603` 也没有画质接受条件。
- 证据：真实格式选择器仍选出 `360-video+audio`。`download.py:623` 只比较“选中流”和“实际文件”是否一致，二者都是 360p 就接受，并记录“画质选择为 1080p，未自动降低画质”。离线调用已复现。
- 建议：在实际获取前按最终选中流核对用户已确认的质量，统一覆盖新建、重试、恢复入口；实际尺寸与接受结果应随任务保存，不以有无前端元数据为前提。

## 3. [P1] 新 original 规则会拒绝合法高清，或忽略更高清的合并流

- 位置：`download.py:178–192`。
- 原因：`bestvideo+bestaudio` 要求分离的视频轨和音频轨，并不等于“所有可用格式中分辨率最高”。
- 真实 yt-dlp 选择器离线结果：
  - 只有一个自带音轨的 3840×2160 文件：选择结果为空。
  - 只有无音轨视频：选择结果为空（OCR 场景也无法获取）。
  - 同时存在合并 4K 文件和分离 360p 视频+音频：选择 360p。
- 建议：先比较所有合法视频格式的实际质量，再决定是否需要合并音频；不要将合并流一概视作低清。这项是最近画质修复引入的回归。

## 4. [P1] 本地翻译等待响应时无法及时取消

- 触发：Ollama 已收到翻译请求、尚未返回时点击取消。
- 位置：`translate.py:791` 同步请求；单工作线程循环 `translate.py:822`；本地 HTTP 读超时 `translate.py:1029–1038`。
- 原因：取消只设置任务标志，没有终止在途 HTTP 请求。必须等请求返回或读超时，后续代码才检查取消。当前本地读超时是 600 秒，不应将其理解成保证的总任务最长时间。
- 证据：隔离阻塞 mock 中，设置取消后线程仍存活；释放响应后才抛出取消异常。在线并发分支的 `wait()` 与 `shutdown(wait=True)` 也有类似等待结构。
- 建议：让在途翻译请求可取消并正确释放客户端资源，而非只在批次前后检查标志；不得结束其他软件共用的 Ollama 服务。

## 5. [P1] 本地模型切换到“推荐设置”会残留错误模型名

- 触发：先选择 Ollama 的 Qwen/TranslateGemma，再点击“应用推荐设置”。
- 位置：`App.tsx:1279–1284`、`translate.py:265–279`。
- 原因：推荐设置将翻译器改为 DeepSeek，却保留 `translate_model=qwen3.5:4b` 等本地模型名。
- 后果：后续请求将本地模型名发给 DeepSeek，导致翻译失败。`workbench_api.py:277` 的在线准备检查仅检查 `/models` 状态码，没有核对所选模型是否存在，可能在检查通过后才失败。
- 证据级别：跨模块代码确认，未真实调用在线服务。
- 建议：切换翻译器时统一处理对应模型值，推荐设置复用同一规则；准备检查核验实际模型与实际服务地址。

## 6. [P2] 字幕页修改样式后直接重渲染，仍使用旧设置

- 触发：在字幕页改字号、颜色等，再点击该页“重新渲染”，没有先回处理页保存方案。
- 位置：`App.tsx:775`、`App.tsx:1887–1900`、`App.tsx:3692` 附近样式面板。
- 原因：修改只更新前端状态；重渲染请求只提交空对象，没有保存最新方案，也没有因方案未保存而禁用。
- 后果：界面说“按当前样式重新渲染”，后端实际使用旧样式。
- 证据级别：请求/状态路径代码确认，未做桌面 UI 操作。
- 建议：该按钮明确保存并应用样式，或提示并阻止未保存方案的重渲染。

## 7. [P2] 即使保存双语模式，重渲染仍烧录旧单语 SRT

- 触发：已有中文单语字幕，保存“原文在上+中文在下”后只重新渲染。
- 位置：`workflow.py:55` 将显示模式变化仅映射到 render；`workflow.py:575–592` 直接读已有 SRT，没有用活动字幕 JSON 重新生成显示文本。
- 证据：构造中英文均存在的活动 JSON 和旧单语 SRT；以双语选项调用真实 `run_render`、仅替换视频编码器，传入编码器的 SRT 仍不包含原文。
- 建议：渲染前从当前活动字幕 JSON 按当前显示模式生成候选 SRT；不必重新调用翻译模型。

## 8. [P2] 下载超时重试中的取消被误判成降画质失败

- 触发：original/1080p 第一次下载超时，第二次重试时取消。
- 位置：`download.py:592–605`。
- 原因：重试捕获所有 `Exception`，把 `CancellationRequested` 也包装成 `DownloadQualityConfirmationRequired`。
- 证据：第一次模拟超时，第二次抛出取消，最终异常是 `DownloadQualityConfirmationRequired` 而不是取消异常。
- 后果：用户明明点击中断，界面却显示失败并要求降低画质，任务状态错误。
- 建议：取消异常优先原样向上传递，只有真实的同画质下载失败才生成相应建议。
